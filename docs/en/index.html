Miniapps

Your agents no longer just answer. They build your tools.

An expense tracker, a dashboard, a shared list: ask the agent and it writes a miniapp — a React front and its server-side handlers — that shows up in the Miniapps tab, in AgentUI’s own look.

In AgentUI’s look

A real app, not a web page glued next to it.

The agent gets a kit of React components and the theme’s CSS variables: the miniapp follows the app’s light or dark mode, language and mobile layout, without a single hardcoded style.

  • Ready-made components: forms, lists, tables, charts
  • Designed phone-first
  • Live update when the agent changes the miniapp
agentui_miniapp_write

The agent writes

It reads the guide shipped with the plugin, then sends its files with agentui_miniapp_* tools. Build errors come back with the file and line: it fixes them on its own.

AgentUI builds and isolates

The front runs in a sandboxed iframe with no access to your session. Handlers run in an isolated worker, with their own data, behind AgentUI’s authentication.

The miniapp appears

It is in the Miniapps tab right away. A cron or the agent can push new data: the open miniapp refreshes by itself.

Data and API

A backend per miniapp, nothing to host.

Each miniapp has its own document collections and key/value store, isolated from the others. Its handlers can call public APIs to show live data; your server’s internal addresses stay unreachable.

  • Routes behind the AgentUI session, one namespace per miniapp
  • Outgoing HTTP calls are bounded (time, size, public addresses only)
  • The agent reads and writes data with agentui_miniapp_data
A miniapp only reaches its own routes and data: not your conversations, not other miniapps.
Scheduled tasks

Your agents work through the night. You find everything when you wake up.

Morning briefings, watchers, backups… Every cron task of your agents has its own conversation: the result arrives as a real message, widgets included.

Cron messages

The result lands in the task’s conversation.

The agent doesn’t wait for you to talk to it: on every run, it posts a proactive message in the “⏰ task name” conversation. You can reply and carry on from that result.

  • One conversation per task, filed under “Cron tasks”
  • “Unread” dot and a “New message” marker
  • Tables, lists and other widgets inside the message

The task runs

The platform’s scheduler (Hermes, OpenClaw…) starts the task on time — a prompt handed to the agent, or a plain script.

The message arrives

The plugin forwards it to AgentUI, which files it in the dedicated conversation. It is created automatically on the first run.

You get notified

A push notification appears; one tap opens the right conversation, even if the app was closed.

“Tasks” page

What worked, what failed — and why.

Schedule, next run, last status: all on one page. When a task fails, the full error message is one click away — no digging through server logs.

  • Status and error of the last run
  • Direct access to the task’s conversation
  • Pause, resume, “Run now”, delete
A task posts to AgentUI when it is configured to deliver its results there; its failures can follow the same path.

How it works

One plugin, one protocol, zero hacks.

AgentUI connects to your platform the way Telegram connects to a bot: through a channel plugin that speaks a simple WebSocket protocol.

Install the plugin

Plugins are provided for Hermes and OpenClaw. The platform opens the connection to AgentUI — nothing to expose on its side.

The agent gets new tools

Chart, table, map, progress, code, form… described as real tools, with their schemas.

The interface does the rest

The agent calls the tool and places the token in its answer. AgentUI swaps it for the component, live while streaming.

// The agent calls a tool…
agentui_chart({
  kind: "line",
  title: "Monthly revenue",
  unit: " k€",
  x: ["Jan", "Feb", "Mar"],
  series: [{ name: "2026", y: [96, 103, 112] }]
})

// …and places the token in its answer:
"Here is the trend: [[agentui:a3f9c1]]"

// AgentUI renders the chart right there.
Comparison

Where AgentUI stands, honestly.

Against messengers (Telegram, Discord…) and web interfaces that go through the API (Open WebUI, Hermes WebUI…). Each approach has its strengths.

MessengersTelegram, Discord, WhatsApp…Web UI via APIOpen WebUI, Hermes WebUI…AgentUIChannel plugin + PWA
Several conversations~Topics or threads, depending on the messenger✓Yes✓One distinct session per conversation
Rich rendering (charts, tables, maps, forms)✗Text and buttons~Markdown, depends on the tool✓Widgets called like tools
Tools, reasoning, sub-agents, cost✗Not shown~Partial, depends on the API✓Native protocol events
Approvals and questions mid-run~Inline buttons, DIY✗Not in a chat API✓Native, the run carries on
Proactive messages (crons, reminders)✓Yes✗No channel for the agent✓Dedicated “Messages from the agent” chat
Managing scheduled tasks and skills✗No~Depends on the UI: some allow it✓Pause, run, errors, reading
Mobile push notifications✓Excellent, nothing to set up~Varies by tool~Yes, but HTTPS required (iPhone: home screen)
Agent behind a NAT✓Yes✗The API must be reachable✓Outgoing connection from the plugin
Data under your control✗Goes through a third party✓Self-hosted✓Self-hosted
Setup✓Almost nothing~A UI to install and wire up~A service + one plugin per platform
Maturity and community✓Very mature✓Large communities✗Young, a single maintainer
Independence from the platform✓Good✓Very good (standard API)~A plugin to maintain for Hermes, OpenClaw…

✓ well covered · ~ partial or with caveats · ✗ missing or poorly suited. General assessments, which vary by tool and version.

In short. To simply talk to an agent from your phone, a messenger is enough and takes less effort. For a general-purpose or multi-user chat interface, a UI via API is more complete. AgentUI targets real agents: tools, sub-agents, crons, approvals, widgets. The trade-off: one more service to host and plugins to maintain.
